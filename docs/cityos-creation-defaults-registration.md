# Compiler-authored component creation defaults

## Contract and ownership

This is a bounded implementation guide for `cityos.puck.registration.v4`.
It extends the existing parser and binder; it is not a second compiler,
component registry, authorization engine, or document persistence owner.
The v1, v2, and v3 protocols keep their existing behavior.

V4 requires an explicit `defaultProps` object for each component, including
an empty object when no creation values are authored. Defaults are produced
by CityOS Compiler from the selected locale's validated canonical catalog
source. They are passed to the installed component's Puck `defaultProps`
for creation, not merged into the props of an existing document.

Root defaults are deliberately prohibited. The binder does not repair
missing, withheld, imported, or existing values. Identity fields and slot
instances cannot be supplied as defaults. This change does not create new
nodes, write documents, grant permissions, migrate data, or publish content.

## Validation and compatibility

The compiler checks both language defaults against complete field contracts.
The receiving fork independently validates data-only structure, known field
names, integers, choices, Boolean values, bounded string lists, nested objects,
and record arrays. The full owner constraints remain with the canonical
command boundary and compiler sidecar; editor validation is not authorization.

False, zero, empty strings, duplicate list values, embedded newlines, empty
objects, and empty arrays remain distinct. Optional omitted fields remain
omitted. Input snapshots are frozen before asynchronous digest work, while
separate bound configurations receive separate mutable creation defaults.
Existing graph, byte, depth, renderer-version and implementation-digest checks
remain in force. Cached render functions still reject revoked or changed
implementations. V1-V3 registrations cannot silently opt into default props.

Use the normalized registration digest returned by the compiler, not the
pretty-printed artifact byte digest. The two identities are deliberately
different. No executable module or arbitrary URL is accepted in metadata.
New semantics still require a qualified compiler and receiving implementation.

## Verification and handoff

`scripts/cityos/registration-defaults.test.mjs` contributes 34 independent
parser/binder cases to the existing `cityos-registration` CI profile.
The synthetic v4 fixture is generated by the actual CityOS Compiler.
Its provenance file records the exact producer blob and both digest kinds.
Do not hand-edit its generated bytes to change expected behavior.

Before publication, these cases passed with Node 22.16.0 type stripping and
fixture renderer/field adapters. That establishes this source-level contract,
not the full Node 24 package build, mounted editor, platform integration,
provider, publication, or runtime acceptance. Maintained CI must verify the
actual committed revision without reducing existing tests or thresholds.

The platform producer and independent cases are in
`packages/cityos-compiler/src/universal/targets/studio-puck.ts` and
`packages/cityos-compiler/tests/engineering-compiler/studio-puck-defaults.cases.ts`.
Generate `compileDefaultsFixture('ar').artifacts[0].content` and compare it
with `scripts/cityos/fixtures/compiler-registration-v4.json`; compare the
returned `registrationDigest` with the provenance record separately.

Fork maintainers own protocol compatibility and package qualification.
Compiler maintainers own deterministic emission and canonical source checks.
Host maintainers must publish and pin a verified immutable fork artifact,
authorize contribution discovery, then verify actual insertion, editing,
save/reload, denial and revocation in the real Studio. A source commit does
not update an already released package or install new code in a consumer.
Domain owners retain their own business rules, field permissions and stores.

This slice supports extensible component registration. It does not close
all Studio capability families, owner lifecycles, or deployment automation.
Remaining work includes package/public-entry qualification, actual host
adoption, authorized discovery, unknown-data preservation, supported new
primitives, and connected product acceptance before predecessor retirement.
